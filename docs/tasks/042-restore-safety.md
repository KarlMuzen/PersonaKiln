# Task 042: Restore never overwrites newer or existing local data

Review: required
Goal: Settings, "Restore Database" (merge mode) never replaces a card or lorebook with an older or equal copy, never erases a saved API key, never overwrites a local setting, and tells the user what it kept and what it skipped.
Files to touch:
- `src/io/backup.ts`
- `src/components/settings/BackupRestoreSection.tsx` (result text only)
- `test/backup.test.ts` (one existing test, change 8)
- `test/backupRestoreMerge.test.ts` (new)
Do not touch: `src/db/index.ts` (no schema, hook or Dexie version change), `src/schemas/`, `src/store/`, the export side of `backup.ts` (`createFullBackupJson`, `createFullBackupZip`, `parseBackupPayload`), the overwrite-mode clearing and the vault logic in `restoreFullBackup`, `scripts/smoke.py`, `ConnectionProfilesSection.tsx` and the profile type (card 043). No new dependency. No frozen identifier.
Changes (all in `restoreFullBackup` unless named; code only where the design depends on it):
0. Test first. Create `test/backupRestoreMerge.test.ts` with the same header and `beforeEach` as `test/backup.test.ts` (jsdom, `import '../test/setup'`, clear cards, lorebooks, connectionProfiles, settings). Write test 1 of change 10 first and run it on the unmodified code (`npx vitest run test/backupRestoreMerge.test.ts`). Claude's reading: a keyless backup merged onto an existing profile calls `db.connectionProfiles.update` with `apiKey: undefined`, and Dexie treats `undefined` in an update as a delete, so test 1 should fail before the fix (inferred, not run). Write the real result under Done in the PR description. If it passes, say so and keep the test.
1. Date rule, two private helpers in `backup.ts`. `toSeconds(v)`: not a finite number, or 0 or less, gives 0; above 100,000,000,000 is milliseconds, so divide by 1000 and floor; otherwise as is. `backupIsNewer(local, incoming)` is `toSeconds(incoming) > toSeconds(local)`. Strictly newer only: equal dates, no date on either side, and no date on the backup side all keep the local copy. (The app stores seconds in `cardSlice.ts`; imported cards can carry milliseconds; the tests use `Date.now()`.)
2. Cards whose `uuid` already exists, both modes (in overwrite mode only duplicates inside the file meet this). Not `backupIsNewer(existing.modification_date, card.modification_date)`: leave the local card untouched, `cardsKept++`, no write. Otherwise `db.cards.update` with these fields, each only when the backup value is not `undefined` (never pass `undefined`): `name`, `tags` (`card.tags || []`), `creator` (`card.creator || ''`), `creation_date`, `modification_date`, `order`, `cardData`, `snapshots`, `avatarUrl`, `testSuites`, `scenarios`, `variantOf`, `variantLabel`, and `embeddedAssets` only when the restored asset set has at least one entry. Do not write `id`, `uuid` or `schemaVersion`. A new `uuid` still goes through `add` unchanged.
3. Lorebooks: the same rule with `updatedAt`. Replace with `name`, `description`, `lorebook`, `updatedAt`, each only when not `undefined`. Not newer: `lorebooksKept++`, no write.
4. Profiles whose `uuid` already exists. After the existing redaction and decrypt logic, if the incoming profile has no usable key (`rec.apiKey` is `undefined`), the update must not contain an `apiKey` key at all, so the local key stays. A usable key (plaintext, an `enc.v1.` key that decrypts, or the incoming-vault path) still replaces the local key as today. Never put an `undefined` value in a profile update. Add the "API key needs to be re-entered" note only when the profile is new or the local profile has no `apiKey`. New profiles and unknown profile keys are stored as today (`test/backupValidation.test.ts` expects unknown keys kept). Other profile fields are still overwritten by the backup as today; profiles have no date.
5. Settings, merge mode only (overwrite mode and the skipping of device security keys stay as they are). For each incoming setting: (a) key `assistant_chats` with both values plain objects: merged value `{ ...incoming, ...local }` (the local chat wins per card uuid); `put` it only when it adds a uuid, otherwise `settingsKept++`; (b) any other key that already exists locally: leave it, `settingsKept++`; (c) key missing locally: `put`. A failed `put` is no longer swallowed: push `Setting '<key>' could not be saved: <message>` to `errors`.
6. Records without a `uuid`: a card gives `cardsSkipped++` and the note `Card '<name>' has no ID and was skipped.`; a lorebook gives `lorebooksSkipped++` and the same note for lorebooks (use `unnamed` when there is no name). A card or lorebook that fails to save keeps its existing error text and also counts in `cardsSkipped` / `lorebooksSkipped`.
7. Return value. Keep `cardsCount`, `lorebooksCount`, `profilesCount`, `cardsSkipped` and `errors` with the same names; `cardsCount` and `lorebooksCount` now count only records written (added or replaced), not kept ones. Add `cardsKept`, `lorebooksKept`, `lorebooksSkipped`, `settingsKept` (numbers). Kept notes never go into `errors`: `test/backupValidation.test.ts` expects `errors` to equal `[]` after a normal export and restore.
8. `test/backup.test.ts`, test "merge mode preserves local cryptographic & passkey credentials...": the local card `card-111` is created inside the test, after the incoming cards were built, so by `Date.now()` it is the newer one and would now be kept. Give the local card `modification_date: 1000` so the test still proves that a newer backup replaces it. No other change to that file.
9. `BackupRestoreSection.tsx`: add a named export `buildRestoreMessage(res)` and use it in `handleFullBackupRestore`. The message always starts with `Database restored! Restored {cardsCount} cards, {lorebooksCount} lorebooks, and {profilesCount} profiles.` (`scripts/smoke.py` waits for the text "Database restored!", also on a second restore where everything is kept). Then, each on its own line and only when a number is above 0, listing only the non-zero parts: `Kept on this device (same or newer): {cardsKept} cards, {lorebooksKept} lorebooks, {settingsKept} settings.` and `Skipped: {cardsSkipped} cards, {lorebooksSkipped} lorebooks (no ID, or could not be saved).` Then, as today when `errors` is not empty, a blank line, `Notes / Warnings:` and the errors one per line. The old "(N record(s) skipped due to validation errors)" sentence goes. Dialog title, `info` level and the OK button stay.
10. Tests in `test/backupRestoreMerge.test.ts`, each seeded through `db` and restored with `restoreFullBackup(JSON.stringify(backup), 'merge')`; use seconds for dates unless a test says milliseconds:
   1. keeps the local API key when the backup profile has `apiKeyRedacted: true` and no key
   2. keeps the local API key when the backup key is `enc.v1.` text and cannot be decrypted (no session key)
   3. a usable plaintext key in the backup still replaces the local key
   4. an older backup does not replace a newer local card; `cardsKept` 1, `cardsCount` 0, local `cardData` and `modification_date` unchanged
   5. equal dates keep the local card
   6. a newer backup replaces the card and brings `testSuites`, `scenarios`, `variantOf`, `variantLabel`, `avatarUrl`
   7. a newer backup without `testSuites`, `scenarios` or `avatarUrl` does not erase the local ones
   8. seconds against milliseconds: local 1,800,000,000 (seconds) against backup 1,700,000,000,000 (ms) keeps local; local 1,700,000,000 against backup 1,800,000,000,000 (ms) replaces
   9. lorebook: an older backup is kept, a newer one replaces
   10. a local setting (`app_theme` `light` against backup `dark`) is kept and counted in `settingsKept`; a missing setting is added; `assistant_chats` merges per uuid with the local chat winning
   11. a card and a lorebook without `uuid` are counted in `cardsSkipped` and `lorebooksSkipped`, each with a note in `errors`
   12. `buildRestoreMessage`: starts with `Database restored!` in every case including all-kept; shows the Kept and Skipped lines only when a number is above 0

Known limits, not part of this card (logged in `docs/BUGS.md`): when the backup copy wins, its snapshot list replaces the local one; the local undo history of that card stays; edits to test suites, scenarios, snapshots or card order do not bump `modification_date`, so a tie keeps the local copy and a restore does not carry such edits across.
