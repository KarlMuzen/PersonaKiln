- **Overwriting the open card on import or restore leaves the old copy in memory (verified 2026-11-01 at `e3ec01a`; carded: a new card right after 045; `Review: required`).** `importCardRecord` in `src/store/slices/cardSlice.ts`: with `overwriteUuid` it updates `db.cards`, reloads the card list and returns; it never refreshes `activeCard`, `activeCardRecord` or `activeCardEmbeddedAssets`, and it leaves `editor_history_<uuid>` alone. Inferred, not run: if the overwritten card is the one open in the editor, the next edit or autosave writes the old in-memory copy back over the new one (the tab-hide flush in `src/store/useCardStore.ts` writes `state.activeCard` to the database, which supports this). - **Bulk ZIP export overwrites cards with the same or non-ASCII names (verified 2026-11-01 at `e3ec01a`; folded into the 049 batch card, `skip`).** `handleBulkExportAllZip` and `handleBulkExportSelectedZip` in `src/components/GalleryView.tsx` build the file name with `name.replace(/[^a-z0-9_-]/gi, '_') || 'card'` and call `zip.file(filename, bytes)` with no check for an existing name. Two cards called "Aria", or two names written in Japanese or Cyrillic (every such character becomes `_`), land on one file, and the toast still says all cards were exported. Fix: add a counter suffix on a repeated name and count the files written.
- **PNG extra assets are corrupted on import and not written on export (verified 2026-11-01 at `e3ec01a`; carded: a new card before 051; `Review: required`, `src/io`).** `importCardData` in `src/io/index.ts` takes the `chara-ext-asset_:` chunks as base64 strings and stores `new TextEncoder().encode(base64Val)`, which is the text of the base64, not the decoded bytes. `exportCardData` for `png` calls `writeCardToPng(validatedCard, { basePng, backfillV2 })`; `writeCardToPng` (`src/io/png.ts`) has no extra-assets parameter at this SHA, so assets are dropped on PNG export. Inferred: an exported CHARX of such a card carries the corrupted bytes. Unverified: how many real PNGs carry these chunks; a real fixture should come with the card.
- **Storage limits are enforced on add but not on update (found 2026-11-01 when Muse's first run of card 045 stopped; Claude re-read the hook at `main` `65c7559`; Post-v1.0, decide together with the real-card limits work).** In `src/db/index.ts` the `creating` hook runs the strict storage schema on every add, so a new-card import over a limit throws. The `updating` hook parses only when `'cardData' in mods`. Muse's probe on fake-indexeddb (not re-run by Claude): Dexie hands the hook dotted keys (`cardData.data.creator`, `cardData.data.tags`, ...), so the check never matches and `db.cards.update` with a 2,001-character creator stores it with no error. Effects: autosave, a cover save and an overwrite import write over-limit values silently, while a new-card import of the same card fails, so a card that saved fine in the editor can fail to import after export. The `lorebooks` updating hook has the same `'lorebook' in mods` check (inferred, not run). Claude's call for v1.0: do not tighten it. Enforcing on update needs a `Review: required` change in `src/db` (merge the mods into the stored object and parse that), and any card already stored over a cap would then fail every autosave, with a card switch still losing the edit (entry below). The alternative is to drop or raise the caps. Decide after real-card fixtures.
- **Storage schemas drop unknown fields on add (verified 2026-11-01 at `e3ec01a`; Post-v1.0, needs a real fixture first).** In `src/schemas/cardSchema.ts` the import schemas end in `.passthrough()` (`LorebookEntrySchema`, `LorebookSchema`, `CharacterCardV3DataSchema`, `CharacterCardV3Schema`); the storage schemas (`LorebookEntryStorageSchema`, `LorebookStorageSchema`, `CharacterAssetStorageSchema`, `CharacterCardV3DataStorageSchema`, `CharacterCardV3StorageSchema`) do not. The `creating` Dexie hook in `src/db/index.ts` runs them on every add and stores the parsed result; on update the hook parses only when it sees `cardData` whole (see the add-but-not-update entry), so stripping on a later edit is less certain than first written. Inferred, not run: Zod's default object schema removes keys it does not know, so unknown top-level card keys and unknown lorebook entry keys disappear at the first save. Not checked: `docs/DECISIONS.md` (read 2026-11-01; no decision on stripping found) and what `normalizeLorebook.ts` already moves into `extensions`.
- **Cancelling the unlock prompt still sends the request (verified 2026-11-01 at `e3ec01a`; Post-v1.0).** `sendSingleLLMRequest` in `src/services/llmAdapter.ts` calls `getDecryptedApiKey(profile)` in a try/catch that falls back to `profile.apiKey`; `sessionSlice.ts` throws when the person cancels the unlock. With a locked vault the stored `enc.v1.` value goes out as the key and the card text goes to the provider, which rejects the key. Claude's call: a bug, not a key leak (the ciphertext is useless without the vault key and the person chose to send to that provider); the request should not be sent after a cancel.
