- **PNG extra assets, leftovers after card 055 (PR #55, `f0a94cc`, merged 2026-11-02; found in Claude's review of head `8a4d411`: Claude read the diff, `png.ts`, `charx.ts` and `galleryUtils.ts`; Post-v1.0 unless the owner moves one in).** (a) *A PNG with extras can export larger than this app reads.* `writeCardToPng` throws only when one asset's base64 text is over `MAX_PAYLOAD_SIZE` (20 MB). `readCardFromPng` also refuses a whole file over 20 MB and a `tEXt` chunk whose data (keyword, one NUL byte and the text) is over 20 MB. So extras of about 15 MB raw in total (less the cover) can export a PNG that this app then refuses to import, and an asset within about 20 bytes of the limit passes the writer's check but fails the reader's. The export succeeds, the stored card is intact and the import error is clear. The gap is in card 055's design, not in the executor's work. Fix, as a card of its own (Claude offered to fold it into file 056 and could not: `docs/AI_WORKFLOW.md` keeps a `Review: required` card to one outcome): in `writeCardToPng`, when extras are passed, throw if keyword plus NUL plus text is over the limit or if the finished file is over it, with a message that names the size and points to CHARX export. To decide: refusing to export blocks PNG export for a card with big extras, and no screen lists or removes extras. (b) *CHARX.* Extras are now written into a .charx under the names `chara-ext-asset_:{path}` (`writeCardToCharx` strips only `embeded://`), and `readCardFromCharx` returns every non-card file as `embeded://{path}`, so a .charx import gives back `embeded://chara-ext-asset_:{path}`, which no longer starts with the prefix: PNG to CHARX to PNG does not carry the extras. Before card 055 the bytes in such a .charx were the base64 text. A colon in a zip entry name may trouble some extractors on Windows (inferred, not run). (c) *A stored key `chara-ext-asset_:__proto__` is dropped silently on PNG export:* `exportCardData` writes `extraAssets[path]` on a plain object, and assigning to `__proto__` sets the prototype instead of adding a key (inferred; needs a hand-made PNG); an object with no prototype or a `Map` avoids it. Unchanged by card 055: cards stored before it keep bare keys and corrupted bytes (no migration, as the card said). No real PNG with these chunks has been found (searches on 2026-11-01 and 2026-11-02), so the tests use built fixtures; the round-trip test passes even if the export step wrote no chunks, because the imported cover carries the originals, and the other tests cover the write.
